# Tower Defense Asset Concept Sheet

Create a polished six-option concept sheet for a software-development-themed tower defense game. Use the bundled template and produce six genuinely different, front-facing, low-poly ideas that remain readable from a zoomed-out gameplay camera.

## Production material direction

For Tower concepts, follow the current project `docs/design/Visual_Asset_Guide.md`: prefer clean colour regions suitable for small palette textures, with restrained detail and emission. Vertex colours remain an option when continuous gradients, procedural variation or a demonstrated practical benefit better fits the model; record that intent for production. This is a production preference, not a claim that a concept image contains UVs or a usable texture atlas. Preserve the sheet template and do not add technical texture metadata to the artwork.

## Bundled resources

- Template image: `assets/concept-sheet-template.png`
- Detailed rendering rules: `references/render-spec.md`
- Diversity and inference rules: `references/diversity-playbook.md`
- Exact text overlay script: `scripts/apply_labels.py`

Always use the bundled template. Do not ask the user to upload or paste it again.

## Input contract

Only one input is required:

- **Concept**: the asset or enemy to explore, such as `Coding Task`, `Merge Conflict`, `Bug`, `Firewall Tower`, or `Database Core`.

All other inputs are optional:

- asset category or gameplay role
- gameplay behavior
- mood
- palette
- must-include elements
- elements to avoid
- visual references
- whether the user wants review mode or direct generation

Never make the user fill out every optional field. Infer sensible defaults from the concept and the game theme.

## Minimal guided intake

### When the concept is missing

Ask exactly one concise question:

> What concept should I explore? You can answer with only the concept name. Optional details: role/category, mood, palette, must include, or avoid.

Do not ask separate questions for each optional field.

### When the concept is provided

Do not ask for optional information unless there is a genuine contradiction that prevents a coherent result. Infer the missing fields using `references/diversity-playbook.md`.

### Workflow modes

- **Guided mode is the default.** Prepare the brief and six concept directions, then ask the user to approve or revise them before rendering.
- **Direct mode** applies when the user says `generate now`, `render directly`, `fast mode`, `skip review`, or equivalent. Infer missing values and render immediately.

## Stage 1: Build the brief

Infer and prepare:

1. **Title**: `[Concept] Concept Variations`
2. **Subtitle**: one concise sentence explaining the asset's purpose in the game
3. **Category**: one short value such as `Enemy`, `Tower`, `Objective`, `Prop`, `Pickup`, `Hazard`, or `Environment`
4. **Mood**: inferred unless supplied
5. **Palette direction**: inferred unless supplied
6. **Must include / avoid**: respect any user constraints
7. **Six separate visual directions**

If category is not supplied, infer it from the concept. Do not leave `Asset Category` as placeholder text.

## Stage 2: Plan six concepts

Create six concept entries before rendering. Each entry must have:

- **Name**: 1–3 words
- **Description**: 4–8 words
- **Silhouette family**
- **Software-development metaphor**
- **Signature gameplay-readable feature**

Do not use generic names such as `Option 1`, `Variation A`, or `Concept 3`.

Use six fundamentally different conceptual directions. Check the diversity matrix in `references/diversity-playbook.md` before proceeding.

### Guided-mode preview format

Present only this compact review block:

```text
Concept: [concept]
Category: [inferred or supplied category]
Direction: [inferred mood and palette in one line]

01 — [Name]: [Description]
02 — [Name]: [Description]
03 — [Name]: [Description]
04 — [Name]: [Description]
05 — [Name]: [Description]
06 — [Name]: [Description]
```

Then ask:

> Generate this sheet, or revise any direction?

Do not ask the user to confirm each optional field individually.

## Stage 3: Render the concept sheet

Read `references/render-spec.md` before generating the image.

Use `assets/concept-sheet-template.png` as the direct edit target and composition base. Generate one model inside each numbered panel.

Mandatory rendering requirements:

- exactly six concepts
- strict front view only
- orthographic or near-orthographic camera
- same scale, baseline, lighting, and presentation across all panels
- stylized low-poly 3D
- feasible below 2,500 triangles per model
- optimized for a zoomed-out tower defense camera
- large, simple, readable forms
- one dominant idea per option
- no extra panels or footer information
- no turnarounds, environments, arrows, annotations, or technical data
- no model may cover the panel number, name, or description area

Preserve the template's:

- canvas and aspect ratio
- header placement
- dark navy background
- 3 × 2 grid
- panel borders
- floor grids
- number badges
- margins and spacing

During image generation, prioritize the model artwork and keep all header and label areas unobstructed. Exact text will be repaired afterward when a shell/Python environment is available.

## Stage 4: Apply exact text

Image generators may misspell short labels. Whenever shell or Python is available, use the included overlay script after generating the concept artwork.

Create a metadata JSON file with this structure:

```json
{
  "title": "Coding Task Concept Variations",
  "subtitle": "Six readable objective designs for software-themed battles.",
  "category": "Objective",
  "options": [
    {"name": "Task Card", "description": "Bold code badge on folded checklist"},
    {"name": "Sprint Token", "description": "Chunky ticket form with status blocks"},
    {"name": "Build Console", "description": "Framed terminal panel with progress core"},
    {"name": "Logic Knot", "description": "Abstract branching symbol wrapped around task"},
    {"name": "Pipeline Stack", "description": "Modular stages linked into vertical system"},
    {"name": "Commit Seal", "description": "Radial code emblem with locked center"}
  ]
}
```

Then run:

```bash
python scripts/apply_labels.py \
  --template assets/concept-sheet-template.png \
  --input <generated-sheet-path> \
  --data <metadata-json-path> \
  --output <final-sheet-path>
```

The script restores the template's text zones and writes the exact title, subtitle, category, concept names, and descriptions.

If Python or shell is unavailable:

1. Instruct image generation to replace every placeholder with the exact prepared copy.
2. Also include the exact category, names, and descriptions in the chat response so the user can recover them if the rendered typography is imperfect.
3. Never claim the text is exact unless it is visibly exact.

## Stage 5: Quality control

Before returning the result, inspect it against all checks below.

### Template checks

- Six original panels remain in the same positions.
- No extra sections were added.
- Number badges `01` through `06` remain visible.
- No placeholder text remains.
- The top-right shows the actual category, not `Asset Category`.
- Each panel shows the correct unique name and description.

### Camera and readability checks

- Every concept is front-facing.
- No concept is shown in three-quarter, side, or top-down view.
- Models use consistent scale and baseline.
- Concepts remain recognizable at approximately 64–96 pixels tall.
- Thin details and dense text are avoided.

### Diversity checks

- All six outer silhouettes are clearly different.
- All six use different dominant metaphors.
- No option is merely a recolor or accessory swap.
- At most one is a traditional document.
- At most one is a conventional terminal/window.
- At most one is a monitor or screen.
- If three or more options look like the same base object, regenerate them before returning.

### Triangle-budget checks

Treat the 2,500-triangle limit as a design constraint, not a measured claim. Favor:

- low-segment curves
- planar surfaces
- simple bevels
- broad extrusions
- limited floating parts
- limited material count

Do not invent an exact triangle count unless a real mesh was created and measured.

## Final response

Return the finished concept sheet and a short copy block listing:

- category
- six names and descriptions

Keep the response focused. Do not repeat the full internal prompt or the whole workflow unless the user asks.
