# Keystone: application architect iteration

## User direction

The user selected 01 Keystone for further iteration and asked how it could reflect an Application Architect. This selects a concept direction for exploration, not final production-model acceptance. Retain the broad low arch/body, compact hovering character and friendly cyan-eyed face; no goggles or top fins.

## Design reasoning and author review

The earlier arch reads as structural architecture, while generic side ports leave the software role unclear. This exploration makes application composition, responsibility boundaries and data relationships visible. These are visual metaphors, not a prescribed software architecture or a gameplay specification.

1. **System Composer**: the side arch contains an orange application-window component, two service blocks and a data drum with physical bridges. Strongest role cue because the structural bay holds a small application model. The generated routes form a simplified fan-out; production would refine the chosen dependency topology and attachment seats, not treat the image as an exact wiring specification.
2. **Layered Core**: interface, service and data sections divide the deep body front-to-back. The most integrated anatomy and strongest side depth, but its software meaning is less explicit without explanation. It should not be sold as automatically self-explanatory.
3. **Blueprint Planner**: a hinged design leaf makes planning explicit and leaves the face unobstructed. It is readable in the concept view but depends more heavily on a carried diagram-like tool. Deployed width and folded clearance would need a model-stage review.

Recommendation: continue System Composer as the primary role direction; use Layered Core's sectioning only where it clarifies construction without increasing clutter. No option has been accepted by the user. These are illustrative images generated with the built-in image tool, not runtime renders. Canonical r27 Blender and GLB remain unchanged; no animation is authorized here.
