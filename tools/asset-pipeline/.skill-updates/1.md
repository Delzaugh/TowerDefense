# Model Spec Sheet Skill

Create a completed low-poly game-asset presentation sheet using the bundled image at:

`assets/model-spec-sheet-template.png`

The template is the direct edit target. Preserve its 1536 × 1024 canvas, dark navy visual system, panel geometry, labels, spacing, borders, and typography.

## Tower material policy

For Tower assets, read the project's current `docs/design/Visual_Asset_Guide.md`. Prefer small palette textures when making new production design choices; vertex colours remain appropriate when they better support gradients, procedural variation or a documented practical benefit. A specification sheet must report the actual delivered method, image size and verified UVs. Never invent a texture or UV layout, or convert an existing model merely to fill a template panel.

## Required inputs

Use any asset images, sketches, orthographic views, model screenshots, texture maps, wireframes, and written constraints supplied by the user.

Build a compact internal brief from the available information:

- Asset name
- Short description
- Asset type
- Intended game style and camera
- Triangle limit or target platform
- Required silhouette, colors, symbols, expression, limbs, accessories, and proportions
- Verified triangle count, vertex count, texture size, and material count

Do not block the workflow for nonessential missing information. Keep unknown technical values as `-`. Ask one concise question only when the asset itself cannot be identified or no usable visual/design description exists.

## Source-of-truth rules

1. Treat the user's asset references and explicit constraints as authoritative.
2. Preserve the asset's silhouette, proportions, colors, materials, symbols, personality, and construction across every panel.
3. Do not invent limbs, facial expressions, accessories, geometry, text, or gameplay functions that conflict with the references.
4. Do not fabricate triangle counts, vertex counts, texture sizes, material counts, or UV layouts.
5. A stated polygon budget is a hard ceiling. Design and depict economical low-poly geometry appropriate to that budget.
6. If references conflict, prioritize the newest explicit user instruction, then the newest supplied image.

## Template fields

### Header

Replace the placeholders only when corresponding information is known:

- `Asset Name` → supplied asset name
- `Short Subtitle / Description` → one concise sentence
- `Asset Type` → concise role such as Enemy, Tower, Objective, Prop, Building, Pickup, or UI Object

Do not add a Game Name field.

### Turnaround row

Fill the six labeled viewports with the same model:

1. **Front** — straight-on front view with minimal perspective distortion.
2. **Front-Left** — front-left three-quarter view showing depth.
3. **Left** — exact left profile.
4. **Back** — straight-on rear view.
5. **Back-Right** — rear-right three-quarter view.
6. **Right** — exact right profile.

Turnaround requirements:

- Keep model scale, pivot, ground level, camera height, lighting, and materials consistent.
- Use an orthographic or near-orthographic product-render feel.
- Center the model inside every viewport with comfortable margins.
- Use soft contact shadows and restrained studio lighting.
- Do not place scenery, props, labels, or effects inside these six viewports.
- Make left/right and front/back geometry logically consistent rather than generating six unrelated interpretations.

### In-Game View

Fill the lower-left panel with a genuinely zoomed-out gameplay view:

- Use the intended game camera, preferably the user's supplied gameplay reference.
- Show enough environment, path, terrain, grid, neighboring assets, or scale cues to communicate real gameplay scale.
- Keep the asset small—normally around 3–8% of the panel height—unless a supplied game screenshot establishes a different scale.
- Preserve silhouette readability without turning the panel into a close-up.
- Keep the environment stylistically compatible and visually secondary.

### Wireframe

- Prefer a real wireframe or topology screenshot supplied by the user.
- Otherwise create a clearly illustrative wireframe approximation of the same model in a useful three-quarter view.
- Use clean light mesh lines over a dark or slightly transparent surface.
- Keep topology economical and plausible for the stated polygon budget.
- Never derive or claim an exact triangle/vertex count from an illustrative wireframe.

### Texture / UV

Use the best available real production artifact in this order:

1. Supplied UV layout
2. Supplied texture atlas
3. Supplied material/color map
4. Empty template UV grid

Do not invent a production-ready UV layout. When no genuine UV or texture data is supplied, leave the grid empty.

### Model Info

Populate only verified values:

- Triangles
- Vertices
- Texture
- Materials
- Target

Use `-` for unknown values. Concise target examples include `< 2500 tris`, `Mobile`, `PC / Console`, `Unity URP`, `Unreal Engine`, or `Real-time`—but only when supported by the user brief.

### Color Palette

Replace the placeholder swatches with five representative asset colors when enough reference information exists. Include the dominant body color, key accent, darkest value, lightest value, and an important gameplay/readability color. Match the source references closely.

### Notes

Add three short, concrete production notes. Favor statements such as:

- Strong silhouette at gameplay scale
- Readable from an elevated camera
- Optimized for real-time rendering
- Single-material workflow
- Important symbol remains visible at distance
- No limbs or facial animation required
- Designed below the supplied triangle limit

Do not add unsupported claims.

## Image-generation workflow

1. Use `assets/model-spec-sheet-template.png` as the direct edit target.
2. Include all relevant user asset references in the same image-generation/edit request.
3. Instruct the image model to preserve the template layout exactly and replace only its placeholders and empty panels.
4. Explicitly state the invariant asset features that must remain identical in all views.
5. Explicitly state forbidden changes, especially unwanted limbs, expressions, accessories, symbols, or palette shifts.
6. Request one completed 1536 × 1024 sheet rather than separate loose renders.
7. Inspect the result for consistency and regenerate/edit when major geometry, labels, panel content, or orientation is wrong.

Use the detailed prompt scaffold in `references/render-prompt.md` when preparing the image edit.

## Quality gate

Before delivering the final sheet, verify:

- The template structure and canvas are preserved.
- All six views depict one coherent model.
- Front/back and left/right orientations agree.
- The in-game view is visibly zoomed out.
- No example model remains from a previous sheet.
- No unsupported technical statistics were invented.
- The triangle-budget guidance is respected visually.
- All visible labels are legible and correctly spelled.
- Unknown UV/model fields remain blank or `-`.
- No Game Name field appears.
- The result reads as one professional low-poly game-asset spec sheet.

## Deliverable

Return the completed PNG. Briefly mention any technical fields intentionally left as `-` because the user did not provide verified values.
